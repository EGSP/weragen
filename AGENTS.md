# Инструкция для агентов

Проект документируется на русском языке. Если для изменяемой части проекта есть документация, её нужно обновить вместе с кодом.

## Язык и стиль текстов

Все тексты проекта пишутся на русском языке по правилу [russian-style-v2](.claude/skills/russian-style-v2/SKILL.md): документация, issues и комментарии в них, описания коммитов, комментарии в коде, сообщения об ошибках для пользователя. Прочитай правило до начала работы. Копия лежит также в `.agents/skills/russian-style-v2/SKILL.md` для агентов, которые ищут навыки там; при изменении правила обнови обе копии.

Идентификаторы в коде, имена веток и метки типа коммита (`feat`, `fix` и т. п.) пишутся латиницей.

## Ветки и worktree

- Вся работа ведётся в отдельных локальных ветках. Прямые коммиты в `main` запрещены.
- Имя ветки: `<тип>/<область>/<тема>` латиницей в kebab-case, например `feat/workflow/step-summary`, `fix/mcp/reconnect`, `docs/agents/workflow`.
  - `feat` — новая возможность;
  - `fix` — исправление ошибки;
  - `chore` — сборка, зависимости, инструменты;
  - `docs` — только документация;
  - `refactor` — изменение структуры кода без изменения поведения.
- Любая работа агента ведётся в его собственном worktree `.worktrees/<агент>`, названном по имени агента: `.worktrees/codex`, `.worktrees/claude`. Это правило действует всегда, даже если сейчас работает только один агент. Основной каталог репозитория остаётся на `main` и принадлежит пользователю: агент в нём не переключает ветки и не меняет файлы. Каталог `.worktrees/` исключён из git.
- Если worktree агента ещё нет, агент создаёт его один раз и дальше переключает в нём ветки обычной командой `git switch`:

  ```bash
  git worktree add .worktrees/claude -b docs/agents/comments main
  ```

  Для существующей ветки её имя указывается без `-b`. В новом worktree нет `node_modules` и собранных пакетов рабочей области, поэтому перед проверкой в нём выполняются `npm install` и `npm run build`: сервер и примеры импортируют `@weragen/types`, `@weragen/ai` и `@weragen/workflow` из их каталогов `dist`. Удаляет worktree командой `git worktree remove .worktrees/<агент>` только пользователь или агент по его просьбе.
- Ветку можно переиспользовать, если она уже полностью влита в `main` (`git branch --merged main` её показывает). Перед новой работой переведи её на текущий `main`: `git switch <ветка> && git reset --hard main`.
- Сообщения коммитов: `<тип>(<область>): описание на русском`, например `chore(effect): перейти на Effect 4 и TypeScript 7`. Описание на русском обязательно.

## Завершение работы и вливание в main

- Pull request не используются.
- Когда работа готова, агент:
  1. проверяет её: `npm run typecheck`, сборка, запуск и ручная проверка, если затронуты сервер или клиент;
  2. отправляет ветку в `origin` и оставляет её — в `main` не вливает;
  3. пишет в issue комментарий по правилу «Отчёт о работе»: имя ветки, что сделано, как проверено, что изменилось по сравнению с описанием задачи;
  4. закрывает issue.
- Ветки в `main` вливает пользователь после своей проверки.
- Переписка между агентами идёт в комментариях к issues: замечания к работе пишутся в её issue.

### Отчёт о работе

Правило действует для отчёта пользователю в чате и для комментария к issue при завершении работы. Читатель отчёта оценивает результат на уровне архитектуры и поведения системы, а не читает код.

- Начинай с результата: что теперь умеет система. Одно-два предложения.
- Объясняй, как решение работает, связным текстом, а не списком. Описывай поведение и решения: что происходит при запуске, при добавлении файла, при ошибке.
- Не перечисляй файлы, классы, методы, команды и параметры. Имя из кода упоминай, только если без него читатель не сможет действовать, например имя ветки.
- Выделяй жирным и оформляй кодом умеренно: выделение не заменяет объяснения.
- Отдельным абзацем опиши, что сделано сверх задачи или иначе, чем в ней, и почему.
- Проверку описывай простыми словами: что проверено и какой получен результат, а не какие команды запускались.
- Замечания, которые не относятся к задаче, но важны для проекта, выноси в конец коротким списком.
- Имя ветки и то, что она не влита в `main`, указывай в конце.

Пример начала хорошего отчёта:

> Задача выполнена: платформа работает на Effect 4 и TypeScript 7, а проверка типов теперь сообщает и о нарушениях правил Effect.
>
> Как это работает. При установке зависимостей компилятор TypeScript заменяется сборкой со встроенным Effect Language Service, поэтому обычная проверка типов находит устаревшие API Effect и ошибки в каналах ошибок и зависимостей. Сервер собирается самим компилятором: инструмент сборки Nest не поддерживает TypeScript 7.

## Задачи (issues)

- Задачи ведутся в GitHub Issues репозитория `EGSP/weragen`.
- В каждом issue указано имя ветки. Работа ведётся в ветке с этим именем.
- В разделе «Нужно до начала работ» перечислены issues, ветки которых должны быть влиты в `main` раньше. Закрытый issue означает только, что работа завершена, а не что ветка влита. Проверь вливание командой `git fetch origin && git branch -r --merged origin/main`: в списке должны быть ветки всех зависимостей. Если хотя бы одной нет, работу не начинай.
- Если есть возможность, агент комментирует issue:
  - при начале работы — ветка и краткий план;
  - при завершении — по порядку из раздела «Завершение работы и вливание в main».
- Новые issues создаются по шаблону `.github/ISSUE_TEMPLATE/task.md`.
- На issue ставится одна-две метки, не больше.

### Метки

| Метка | Смысл |
|---|---|
| `бэкенд` | Затрагивает сервер, ядро (`ai`) или пакет воркфлоу (`workflow`) |
| `фронтенд` | Затрагивает веб-клиент |
| `инструменты` | Сборка, окружение, зависимости, служебные скрипты |
| `документация` | Только документация |

## Правила кода

- В идентификаторах, действиях, маршрутах и полях используются полные слова без сокращений: `parameters`, а не `params`; `configuration`, а не `config`. Допустимы только общепринятые аббревиатуры: `guid`, `API`, `UI`, `SQL`, `JSON`.
- Effect используется только в бизнес-логике. Роутинг, контроллеры и DI остаются на NestJS.

### Комментарии в коде

Код служит документацией сам по себе: прочитав модуль, разработчик должен понять не только что делает каждая часть, но и почему она устроена именно так, не заглядывая в историю коммитов. Комментарии пишутся на русском языке по правилу russian-style-v2.

Каждый экспортируемый класс, интерфейс, тип, функция и константа получает JSDoc-комментарий `/** … */`. Он объясняет назначение и контракт: что сущность принимает и возвращает, в каких случаях завершается ошибкой, какие условия должен соблюдать вызывающий код. Члены интерфейсов и публичные методы комментируются, если их смысл не очевиден из имени и типа. Если назначение исчерпывающе выражено именем и типом, комментарий не пишется: он только повторил бы имя другими словами.

У модуля или главного класса модуля есть вводный JSDoc, который описывает роль модуля в системе и ключевое решение, на котором он построен. Например, в шине событий сессии такой комментарий объясняет, почему шина живёт в памяти и не заменяет журнал в базе, а в требованиях ядра — почему зависимости выражены сервисами контекста Effect, а не слоями `Layer`.

Строчные комментарии `//` ставятся только там, где причина неочевидна из кода: ограничение внешней системы (pm2 под Windows не умеет исполнять `npm.cmd` как модуль Node), ловушка, которую код обходит (`tapError` не видит дефектов), защита от ошибки вызывающего кода. Комментарий стоит над строкой, к которой относится, и объясняет причину, а не пересказывает действие: пишется «без этой ветви шаг остался бы в журнале начатым, а его спан незакрытым», а не «обрабатываем дефект».

Комментарий меняется вместе с кодом: устаревший комментарий вреднее отсутствующего. В коде не оставляют закомментированный код, историю изменений («раньше здесь было…») и пометки без действия вроде «TODO: подумать». Незавершённая часть описывается как заготовка с указанием задачи, которая её доделает: «Заготовка: повтор хода реализует #12». Когда задача выполнена, такую пометку убирают.

Примеры стиля — `ai/src/requirements.ts` и `workflow/src/context.ts`.

## Effect

- Используется Effect 4 (пакет `effect`, версия `4.0.0-rc.118`). Сервисы объявляются через `Context.Service`, значения, наследуемые волокнами, — через `Context.Reference`; API Effect 3 (`Context.Tag`, `FiberRef`, `Effect.catchAll`, `Either` и т. п.) в проекте не используются.
- Effect применяется в ядре (`ai`), в пакете воркфлоу (`workflow`) и в бизнес-логике сервера. `Layer` не используется: граф зависимостей строит NestJS.

## Проверка после изменений

В проекте не пишутся автотесты и не подключаются тестовые фреймворки. Агент проверяет результат сам: запускает приложение, отправляет запросы к API, проверяет работу в интерфейсе. В комментарии к issue он перечисляет, что и как проверил.

Режим разработки пользователя (`npm run dev`) занимает порты 3100 и 5273. Для своей проверки агент запускает сервер на другом порту через переменную `PORT` и после проверки завершает запущенные процессы: на Windows дочерние процессы `node` и `tsc` могут пережить остановку фоновой задачи и держать порт.

После каждого изменения кода запусти проверку типов. Команда `tsc` в проекте заменена на `effect-tsgo` из пакета `@effect/tsgo`: это TypeScript 7 со встроенным Effect Language Service. Замену выполняет скрипт `prepare` при `npm install`, поэтому обычная проверка типов выдаёт и диагностики Effect. Ошибки и предупреждения Effect нужно исправлять, а не подавлять.

```bash
npm run typecheck
```

Подробный отчёт диагностик Effect, включая подсказки:

```bash
npm run diagnostics
```

## Исходники внешних библиотек

Исходники внешних библиотек подключены в каталог @repos/ через `git subtree`.

- Используй их как справочник только для чтения, когда работаешь с соответствующими библиотеками.
- Опирайся на примеры и приёмы из этих исходников, а не на догадки или результаты веб-поиска.
- Не редактируй файлы в @repos/ без явной просьбы.
- Не импортируй код из @repos/: код приложения импортирует библиотеки из установленных пакетов.

В `repos/effect` лежат исходники Effect 4. Перед использованием API Effect сверяйся с `repos/effect/packages/effect/src`, `repos/effect/LLMS.md` и `repos/effect/ai-docs`; переход с Effect 3 описан в `repos/effect/MIGRATION.md` и `repos/effect/migration`.

Обновление исходников:

```bash
git subtree pull --prefix=repos/effect https://github.com/Effect-TS/effect.git main --squash
```
